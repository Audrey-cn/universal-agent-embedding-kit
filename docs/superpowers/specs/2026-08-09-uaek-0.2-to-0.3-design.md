# UAEK 0.2 Release Closure and 0.3 External Evidence Design

**Date:** 2026-08-09  
**Status:** proposed for implementation  
**Owner:** UAEK maintainers

## Objective

Close the already-implemented UAEK 0.2 runtime as a coherent release candidate, then make
0.3 an evidence-strength release instead of another horizontal feature expansion. Completion
means that version claims, documentation, audit artifacts, tests, and remote CI agree; the 0.3
tooling can reproducibly ingest and evaluate multi-sample live evidence, cold-path cost evidence,
long-session scenario evidence, and an approved external baseline.

The project must continue to report unavailable external evidence as unavailable. A missing
credential, provider quota, approved baseline, PyPI token, or spending authorization is an
external gate, not permission to synthesize a successful result.

## Approaches Considered

### A. Sequential release closure, then evidence campaign — selected

First remove 0.2 release ambiguity and strengthen the truth gates. Then build 0.3 evidence
contracts and campaign tooling. Finally run only the externally authorized campaigns.

- Advantage: every later artifact is produced by a versioned, internally consistent release.
- Advantage: failures are attributable to either product behavior or external evidence, not
  mixed with stale release metadata.
- Cost: delays new live runs until the release truth plane is reliable.

### B. One large 0.2/0.3 change set

Change versions, documentation, audit semantics, provider campaigns, scenario ingestion, and
cost aggregation together.

- Advantage: fewer intermediate milestones.
- Rejected because: a failed live campaign would block unrelated release hygiene and create an
  unreviewable change set.

### C. Skip 0.2 closure and work only on research evidence

- Advantage: fastest route to new benchmark numbers.
- Rejected because: current version and audit drift would make stronger evidence harder to trust
  and harder for third parties to reproduce.

## Scope Decomposition

The work is split into three independently testable subprojects. Each receives its own
implementation plan.

1. **0.2 release closure:** version authority, documentation truth, audit consistency, support
   status, focused regression coverage, and a clean release-candidate gate.
2. **0.3 evidence contracts:** repeatable campaign manifests, backend-family identity,
   multi-sample aggregation, cold-path cost ingestion, long-session scenario ingestion, and
   external-baseline validation.
3. **0.3 campaign execution:** run credentialed providers, archive artifacts, execute an approved
   external baseline, and optionally publish packages. This subproject is externally gated.

## 0.2 Release Closure Design

### Version authority

`pyproject.toml` is the release source of truth. Runtime surfaces obtain their version through
`importlib.metadata.version("uaek")`, with a source-tree fallback in one small version module.
CLI, `src.__version__`, default configuration, HTTP health output, MCP initialization, changelog,
and badges must report the same release line. The target is `0.2.0rc1`; advanced capabilities that
do not meet the supported contract remain explicitly experimental.

### Documentation truth

The active plan becomes the canonical To Do list. The old four-phase execution manual is marked
historical and points to the current architecture, active plan, and release checklist. References
to missing `PROGRESS_TRACKER.md`, obsolete fixed test counts, and outdated 10/30/40 scenario or
4/4 provider statements are removed or corrected.

### Audit truth

Audit gates must be derived from suite results and explicit evidence rather than hard-coded
booleans. In particular:

- capability completeness comes from the strict full-suite provider count;
- live-matrix completeness comes from the live-matrix result;
- external-baseline availability comes from the loaded baseline;
- CI verification records run URL, artifact URL, and commit SHA;
- consistency checks fail on contradictory scenario counts, provider counts, version claims, or
  stored headline/limitation text.

`audit_passed` continues to mean that the audit executed without incomplete required suites or
internal contradictions. It does not mean all five research propositions are complete.

### Supported versus experimental capabilities

The 0.2 support matrix identifies public supported paths and experimental modules. Supported
paths include the CLI/API/MCP shared workflow contract, core verification runners, effort,
memory persistence, security checks, audit, and packaged entrypoints. Advanced render, formal,
multi-perspective, cognitive-panel, and incremental modes remain experimental unless focused
contract tests demonstrate their advertised public behavior.

The global 75% coverage floor remains for 0.2, but a regression test prevents supported critical
modules from silently falling below their recorded baseline. Coverage growth must come from
behavior tests, not exclusions.

## 0.3 Evidence Contracts Design

### Campaign manifest

A versioned JSON manifest describes an evidence campaign without embedding credentials. Each
provider entry identifies:

- provider runtime name;
- actual backend family when known, or `unknown`;
- command recipe and output mode;
- sample count and deterministic seed policy;
- timeout and task suite;
- isolated provider home plus explicit seed paths;
- output directory.

Validation rejects secrets in manifests, zero sample counts, duplicate sample identities,
unsupported output modes, and provider-home seeds without isolation.

### Multi-sample aggregation

Each run artifact records campaign ID, provider runtime, backend family, sample ID, seed,
task-set digest, grader version, result, and failure class. Aggregation reports per-provider and
per-backend-family pass rate, score distribution, confidence interval, timeout/error rate, and
sample count. A platform shell routed to another backend does not count as a distinct model
family.

The existing strict 10/10 single-artifact headline remains available for historical comparison,
but the 0.3 headline is the multi-sample backend-family aggregate.

### Cold-path cost evidence

A versioned cost ledger accepts real per-turn input, cache-read, cache-write, output, elapsed-time,
and session-gap data. The aggregator separates warm, mixed, and cold/TTL-miss-heavy cohorts and
reports sample counts and uncertainty. It must never project a warm-session reduction onto the
cold cohort.

### Long-session scenario evidence

A versioned session artifact represents a real multi-step development session: scenario identity,
source/provenance, elapsed duration, turn count, repository/task metadata, checkpoints, final
outcome, and multidimensional grades. A corpus report distinguishes deterministic scenarios from
live sessions; deterministic items cannot satisfy the `100+ live multi-hour` target.

### External baseline

The baseline schema requires an approved name, immutable source reference, model/runtime identity,
evaluation date, task-set digest, sample count, metric definitions, and limitations. Audit accepts
the baseline only when its task and grader contracts are comparable; otherwise it records
`incompatible`, not `provided`.

### External campaign acceptance thresholds

The externally gated campaign has fixed minimums so that completion cannot be declared by
interpretation after seeing the results:

- capability: at least three genuinely distinct backend families, three independent samples per
  backend/task pair, using the same ten-task digest and grader version;
- cost: at least five measured sessions in each warm, mixed, and cold/TTL-miss-heavy cohort;
- scenarios: at least 100 live development sessions, each preserving duration, turn count,
  checkpoints, provenance, and multidimensional grades; the report separately identifies which
  sessions lasted at least one hour;
- baseline: at least one user-approved, immutable, task-compatible replacement baseline with
  three or more samples per task.

These thresholds are evidence targets, not authorization to incur their cost. Until a spending
ceiling and credentials are available, the campaign remains blocked with its required sample
counts visible.

## Data Flow

1. Validate a credential-free campaign manifest.
2. Run provider samples only when authorization and credentials are present.
3. Persist immutable raw artifacts before aggregation.
4. Aggregate by provider runtime and actual backend family.
5. Ingest cost/session/baseline evidence through versioned validators.
6. Generate the unified audit and machine-readable evidence index.
7. Run consistency gates before any README, scorecard, or release claim is updated.

## Error Handling and Safety

- Missing credentials, provider quota, or executable produce explicit `blocked` artifacts only
  when no task executed; partial execution remains `partial` with real scores.
- Provider timeouts are measurement outcomes, not automatically infrastructure failures.
- No credential value may appear in a manifest, log, artifact, test fixture, or Git diff.
- Live execution uses isolated temporary homes and preserves only explicitly approved seed files.
- PyPI publishing, git push, release creation, third-party messaging, and paid provider runs are
  separate external actions. They require available credentials and an explicit spending or
  publication boundary before execution.

## Testing Strategy

- Every behavioral correction follows RED → GREEN → focused regression.
- Version consistency is tested across package, CLI, HTTP, MCP, and default config surfaces.
- Audit tests use contradictory fixtures to prove fail-closed behavior.
- Campaign tests use deterministic fixture providers; no network is required in CI.
- Aggregator tests cover multiple samples, partial runs, timeouts, same-backend aliases, and
  confidence calculations.
- Cost tests prove warm and cold cohorts cannot be conflated.
- Scenario tests prove deterministic and live counts remain separate.
- Baseline tests reject task/grader digest mismatches.
- Completion requires Ruff, Mypy, 619+ full tests, combined coverage, audit semantics, wheel build,
  clean install, CLI/API/MCP smoke, `git diff --check`, and a clean secret scan.

## Completion Criteria

### 0.2 complete

- All public version surfaces agree on `0.2.0rc1`.
- Active documentation agrees on 40 deterministic scenarios and 2/4 strict full-suite providers.
- Latest remote CI URL, artifact, and commit are present in the evidence ledger.
- No audit consistency error exists; partial research propositions remain honestly partial.
- Supported capabilities pass focused tests and the release-candidate gate.

### 0.3 core complete

- All 0.3 schemas, validators, aggregators, CLI entrypoints, audit integration, documentation, and
  credential-free CI fixtures pass.
- Multi-sample results are grouped by real backend family and include uncertainty and failure rates.
- Warm/cold cost and deterministic/live scenario evidence cannot be conflated by schema or audit.
- An incompatible or absent baseline cannot be reported as externally validated.

### 0.3 external evidence complete

- Authorized multi-provider samples, cold-path measurements, live long-session artifacts, and an
  approved comparable baseline have been archived and pass the same audit consistency gates.
- If authorization, credentials, budget, or a comparable baseline remain unavailable, the core is
  complete but external evidence remains explicitly blocked; no completion claim may hide that
  distinction.

## Non-Goals

- Adding another general-purpose workflow, memory, safety, or agent orchestration subsystem.
- Raising benchmark scores by changing constants or weakening gates.
- Treating provider shells as distinct model families when they share a backend.
- Generating synthetic artifacts and labeling them live or external.
- Publishing, pushing, or spending provider quota without the required boundary and credentials.
